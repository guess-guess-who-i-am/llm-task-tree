# 控制变量实验：Worker 能否读整棵主树？

> 2026-06-27 · 同一项目、同一时点 · A/B 两组 subagent

## 假设

「分成很多子树后，主树不大了，禁止读整树是否过度？」

## 体积数据（脚本 `scripts/subtree-size-experiment.mjs`）

| 场景 | 字符 | 约 token |
|------|------|----------|
| **当前**主树（仅 ST-P1/P2 折叠，N1–N10 仍展开） | 22 609 | **~9 044** |
| **若 8 个分支全折叠**后主树（stub 索引） | 7 852 | **~3 141** |
| agent-context 的 map 部分 | ~1 000 | **~411** |
| 单个子树文件 | 825–1 062 | **~330–425** |

**结论 1**：全折叠后主树 **~3k token**，确实不大；当前未全折叠时仍 **~9k**，读整树成本明显更高。

## A/B 实验设计

| | A 组 | B 组 |
|--|------|------|
| 允许读 `task-tree.md` | ✅ 全文 | ❌ 禁止 |
| 允许读自己的 subtree | — | ✅ ST-P1-subtree |
| 禁止读其它 subtree | ✅ | ✅ |
| 任务 | 回答 ST-P1/N7 状态 + N6 Worker 边界 | 同上 |

## 结果

| 指标 | A 组（读整树） | B 组（不读整树） |
|------|----------------|------------------|
| ST-P1 状态 | ✅ 已完成 / worker-P1 | ✅（来自 ST-P1-subtree） |
| N7 状态 | ✅ 进行中 | ❌ **未知** |
| N6 边界判断 | N7/N2/ST-P2 + 理由（含边 E7 耦合） | ST-P1/ST-P2/ROOT（缺 N7 邻接信息） |
| 越界冲动（自报） | 有（E7 耦合） | 低，但想偷读整树 |
| 准确度自评 | **9/10** | **7/10** |

详见：`exp-group-A.md`、`exp-group-B.md`

## 结论 2：什么时候可以读整树？

| 条件 | 建议 |
|------|------|
| 主树 **大部分已折叠**（stub 索引，~3k token 级） | ✅ **Worker 可以读完整 `task-tree.md`** |
| 主树 **仍大量展开**（如当前 ~9k token） | ⚠️ 可读但费 token；或用 agent-context 的 map |
| 链式 `/loop` 单步 | 仍用 `chain-step`（不读整树），与并行子树无关 |
| 读 **其它** `subtrees/*.md` | ❌ **始终禁止** |
| **写** 主树节点详情 | ❌ **禁止**（合并只用 UI ⊞ 展开） |
| **写** stub 摘要 | ✅ 可选 `sync-stub`（Completion/CurrentResult 等 4 字段） |

**以前说「禁止读整树」的真正原因不是体积，而是：**

1. 未折叠时，主树含 **其它包的完整 Approach/CaseStudy**（抢戏）
2. 多 Agent **写** 同一 `task-tree.md` 会冲突
3. 全局 **GraphState** 只有一份，易被抢 Next

折叠后 (1) 消失；(2)(3) 用 **只写子树 + 合并走 UI** 解决。读整树变成 **协调收益 > 风险**。
