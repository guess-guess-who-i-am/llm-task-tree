# 验收阻断与输入交接修复

## 结论

最近的 F1 验收不是模型主动把工作放进“待解决”，而是执行分支没有拿到验收明确要求的 `intake/normalized/wechat`。分支因此只能做方法研究，无法对原消息、对象、事务、上下文和反证逐条核验；继续生成结论会把方法依据冒充事实依据，所以验收正确地阻断了交付。

## 根因链

1. Git worktree 只携带版本库跟踪内容，忽略的聊天资料不会自动出现在候选工作区。
2. 验收问题原先只保存了文本，重启或进入直接执行修复时丢失了结构化 `inputPaths`，修复器不知道要恢复哪些资料。
3. 直接执行的修复桥接只把候选目录当作项目根；原项目已有资料与候选工作区独有资料不能同时交接。
4. 因此修复 Worker 在缺资料时没有可执行输入，产生“无变化”，随后被无进展检查拦下并堆到待解决。

## 已修复行为

- 验收问题保留结构化 `inputPaths`，可跨重启恢复。
- 修复前按每个明确路径分别检查原项目和候选工作区；两处可组合，不再错误选择单一来源。
- 输入先快照并物化到真实修复 Worker；资料不计入代码交付变更。
- 两处都没有精确资料时，在启动模型前返回 `TASK_INPUT_UNAVAILABLE` / `input-handoff`，保留候选，不伪造完成、不重复消耗模型轮次。
- 恢复输入的回执更新调用者共享结果，后续复验仍能看到实际交接记录。

## 验证

- 源码相关组合：149/149 通过。
- Kit 与插件发行副本：显式缺失输入、混合来源输入、双处缺失保护各 3/3 通过。
- 5505 实际服务：源码运行版本 hash 与 `/api/project` 返回值一致；项目根身份一致；当前无活动运行。

## 边界

本次验证的是 IDE 的输入交接和验收恢复机制，没有重新读取或代替用户的私人聊天原文，也没有声称 F1 业务分析已完成。资料真正交接后，原候选可继续进入聊天核查和新一轮验收；若资料仍不存在，系统会给出精确缺失路径，而不是继续空转。

## 依据

- Git `worktree` 文档：每个 worktree 有独立检出和工作目录，不能假设忽略文件会自动出现。
- Bazel Sandbox 文档：执行所需输入必须显式进入沙箱，未声明依赖会造成不可复现或缺输入。
- Temporal Retry Policies：外部条件未改变时重复整个 workflow 不能解决根因，只会重复消耗资源。
