# Agent Instructions

This workspace uses `task-tree.md` as the shared task graph for human-agent collaboration.

At the start of every substantive task in this workspace:

- Read the latest `AGENTS.md` and `task-tree.md` before deciding what to do.
- If `task-tree.md` does not exist, create it using the existing node/edge schema before doing implementation work.
- If the task is broad, ambiguous, or likely to take multiple steps, first help establish or revise the overall task tree: root objective, major subproblems, dependencies, uncertainty, Current, Next, and NextPlan.
- Do not try to execute the whole tree at once. Advance one focused node or a small coherent group of nodes, then update the graph.
- Use `GraphState.Current`, `GraphState.Next`, and `GraphState.NextPlan` to show where the work is currently being pushed and what should be pushed next.
- When a user request changes the research direction, explicitly re-evaluate which node is current; add a new node and edge when the request is a new subproblem instead of forcing it into an old node.
- Check the `SelectedSkills` field on `GraphState.Next` first, then on `GraphState.Current` if the next node has none.
  - If `SelectedSkills` is non-empty, resolve those skill IDs against available session skills and global skill folders such as `~/.codex/skills`, `~/.agents/skills`, and `~/.orchestra/skills`.
  - Load and follow a selected skill only when it is relevant to the current user request. If a selected skill is irrelevant or unavailable, note that briefly in `skill-routing-log.md` and continue with the best applicable workflow.
  - If a selected skill is actually used, record the skill, task node, reason, and result in `skill-routing-log.md`.
  - When no skill is selected but the task obviously matches an available skill, use the normal skill trigger rules and also record the choice in `skill-routing-log.md`.

When you complete, split, abandon, or materially reframe a task in this workspace:

- Before manually editing `task-tree.md`, create a copy in `versions/` with a filename that starts with a timestamp and a human-readable reason such as `将增加...`, `将修改...`, or `将回退...`.
- Update `task-tree.md` in the same turn.
- Represent work items as graph nodes using the existing node schema.
- Represent relationships, dependencies, evidence links, uncertainty, or decomposition links as edges in the `# Edges` section.
- Do not use node status fields such as `active`, `done`, or `blocked`.
- Prefer updating the smallest relevant node or edge instead of rewriting the whole file.
- If a task reveals a new subproblem, add a node and connect it with an edge.
- If a relation is uncertain, still create or update an edge and put the uncertainty in the edge `Notes`.
- Keep node and edge IDs stable unless renaming is necessary; when renaming a node ID, update edge endpoints too.
- Maintain model-owned node fields when useful:
  - `CurrentResult`: summarize what has been achieved by the time execution reaches this node.
  - `RootCauseAnalysis`: summarize why mistakes or confusion happened.
  - `CaseStudy`: include compact classic cases or concrete examples that support the root-cause analysis; this is displayed collapsed in the UI.
- Keep `Input` and `Output` current when the real data source or deliverable changes. For example, if a task changes from project-local skill repos to global skill folders, update the node `Input`; if a UI action only writes a selection for later Codex use, update the node `Output` to say what artifact or field carries that selection.
- After editing `task-tree.md`, briefly mention which node or edge changed.

The frontend autosaves graph edits back to `task-tree.md`, so before making manual changes, read the latest file from disk.
If using the web API to save or restore the graph, pass a clear `reason`; the server will create the version backup.
