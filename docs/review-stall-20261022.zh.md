# 最终验收长期不结束：根因与修复

## 结论与真实案例

机构认证节点 `DOC_S02_ORG_CERT` 的运行 `29f9eee9-5019-4570-9a58-d741fc57a911` 并不是一直做同一项必要检查。执行者约8分钟完成分析后，验收被其他并行任务的无关文件变化反复作废。最初定位的7次取消累计3,086,328毫秒，即51.44分钟；后续旧进程累计出现9次失效。该运行没有成功启动内部并行任务，不能把它当成多Worker性能实验。

本轮模型保持 `gpt-6.1-sol`，不降低模型质量，不增加任务总时限或工具轮数限制。运行记录的上下文窗口是270K，压缩阈值200K；本次长耗时的主要证据不是上下文压缩。

## 首次偏离的三个边界

1. `createReviewInputWatch.observe()` 看到任何命令执行，就将未知依赖扩大为整个项目；`validate()` 发现其他任务的Java/JSP或脚本变化后取消本轮验收。重新开始的检查者不能复用前一轮的推理，形成检查—取消—重做的循环。
2. MCP递归读取深层子树，但服务的 `findDeepSeekNode()` 只查一层，协调器分配只校验主文件。机构节点实际上位于两层链接后的 `subtrees/doctor-DOC_S02-support.md`。因此同一个节点能读、不能正常写回或委派；旧记录中委派失败2次，树写回失败约13次。
3. `createDirectNodeWorkspace.check()` 没把执行者的完整交付说明传给检查者。报告已在隔离工作区保存，检查者却需要重新查找证据、重做定位。

## 修复机制

- 共用递归链接树解析器，读、写和协调器校验遵循同一棵选定树及其链接子树，仍排除其他独立树和孤立文件。
- 传递执行者交付作为证据定位线索，不把自述当成验证结果；软件实现仍检查相关行为，分析任务不额外要求启动未改动的业务服务。
- 检查者在终结回执中说明全部实际依赖；确定完整时，只缩小原先未知命令造成的全项目兜底范围。宿主指定范围、实际文件读取和本任务交付文件始终受到保护；依赖真的变化仍重新验收。
- 不知道完整范围时明确 `complete=false`，保守检查，不猜测依赖。既有工具契约兼容，新直接验收入口要求提供这项声明。
- 缺回执字段时，在同一会话只补最终回执，关闭其他工作工具，避免重做验证。真实模型首轮实验曾遗漏可选字段并继续失效，因此不能仅靠提示词或模拟测试宣称修复。
- 增加依赖快照、核验和实际依赖回执的计时记录，便于区分模型等待、Hook、文件扫描和业务检查。

## 协调器实际做什么

现在的协调器是宿主程序，不是一个始终替用户思考的总管模型。它接收目标、已分任务、共享接口与工作区状态，安排可执行任务，逐个合入，处理冲突和恢复检查点，最终组织独立验收。这次修复其深层节点识别和交付传递，不声称新增了智能全局规划器。

## 真实续接又发现的两个遗漏

第一次更新后，前3轮模型调用正常；后续网关在HTTP200的SSE流中返回“Request timed out.”或“Request failed.”。原处理把它们当成可继续的普通截流，不断加入宿主续接文字；当时约50K输入，未达到200K压缩阈值。现在识别流内上游超时、失败地址移到已配置备用地址之后；空失败按同一输入重试，不增加上下文、不重放工具。同一输入连续空失败达到API请求重试策略后明确失败，不把任务伪装成仍在推进。没有增加工具轮数或任务总时限，也未切换模型。当前GPT只配置了一个地址，未知备用地址没有被猜测或启用。

第二次真实业务验收虽能完成检查，仍返回无法确认完整依赖范围，因此保守全项目核对。药品页面和另一权限资源脚本的改动再次触发2次重做。进一步定位：协调器已有完整范围入口，直接节点的HTTP入口和持久化白名单却未接收、传递和保存它。现已补齐直接运行、显式续接、服务重启恢复和公开状态的同一契约；非法范围在启动任务前拒绝。新增2项真实HTTP回归先失败后通过，相关28项检查通过；不是通过迫使模型谎报完整范围来消除作废。

最终恢复由宿主根据本任务报告、规则、来源树及机构/项目源码模块明确传入完整范围，包含相关传递服务和数据层，排除无关药品页面与其他任务脚本；检查者直接读取的额外文件仍自动受到保护。没有据此宣称未知任务的范围已经能自动精确推断：缺少完整范围时仍保守核验，自动任务分配今后应继续携带可靠依赖边界。
