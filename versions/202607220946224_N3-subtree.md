## N3 - 让 Codex 同步维护任务图
- Position: 2052,950
- Size: 400,720
- Completion:
- Problem: 如果 Codex 完成任务后只在对话里说明，图谱和真实任务进展会再次分叉。
- Approach:
  - 在 AGENTS.md 中加入完整的树维护协议，覆盖任务开始、任务结束、字段更新、版本备份、skill 路由、检查清单。
  - 协议按 §1~§8 组织：开始前读树/建树/定 Current/Next、结束后备份并更新 CurrentResult/RootCauseAnalysis/CaseStudy/Input/Output/NextIdea、GraphState、边关系。
  - 每个实质任务开始时先读取 AGENTS.md 和 task-tree.md；如果没有 task-tree.md，就先按 schema 建立任务树。
  - 对宽泛任务先建立或修订整体树，再按 Current/Next/NextPlan 逐节点推进，不一次性执行完整棵树。
  - 当用户请求改变研究方向时，重新判断 Current/Next；必要时新增节点和边，而不是硬塞进旧节点。
  - 开始执行时读取 GraphState.Next/Current 节点的 SelectedSkills；如果有选择，则解析全局 skill 并记录实际使用到 skill-routing-log.md。
  - 当真实输入源或输出物发生变化时，同步更新节点 Input/Output，避免任务图显示旧上下文。
- Input: 当前任务进展、用户反馈、实现变更、task-tree.md 最新内容。
- Output: 与实际工作进度一致的任务图。
- Metrics:
  - Codex 每次完成实质性任务后，task-tree.md 中对应节点或边有最小必要更新。
  - 新任务进入时不会绕过任务树；没有树则建树，有树则先读树。
  - 宽泛任务会先形成可见分解，再逐节点推进。
  - Current、Next、NextPlan 能反映当前研究方向。
- Notes: 规则要求不要使用 active/done/blocked 这类节点状态，而是用节点内容和边关系表达局面。
- CurrentResult: AGENTS.md 已重写为完整树维护协议（§1~§8）。v2 并行试跑 worker-N3 已验证 worker-v2 读树策略：主树 stub 索引 + 子树详文隔离 + 禁止跨包读写；产出 docs/subtree-parallel/v2-N3-findings.md（3 条读树要点，input≈17.8k chars）；本轮未写 task-tree 详文、未读 N6/N7 subtree。
- RootCauseAnalysis: 之前的 AGENTS.md 只说了完成后更新 task-tree.md，但没说具体更新哪些字段、怎么更新、什么时候更新、怎么写才合格。模型可能只更新了 CurrentResult 而漏掉 Input/Output，或者只改 GraphState 而没备份。根因是协议太模糊，缺少字段级指令和好/坏示例。新协议把每个字段的更新时机、内容要求、格式范例都写明了，并加了检查清单。回溯问题的根因是 task-tree.md 是状态回滚，文件系统不是事务型回滚；如果不明确权威来源，模型会把旧聊天记忆和残留文件误当成当前任务状态。
- CaseStudy:
  - case 1: 之前 N4 的 Input 还是三个本地仓库，但实际已改为全局 skill 目录，说明 AGENTS.md 没有强制要求 Input/Output 随数据源变化同步更新。
  - case 2: 之前更新节点时有时备份有时不备份，因为 AGENTS.md 只说备份再编辑但没有规定备份时机和命名格式。
  - case 3: CurrentResult 经常写得太笼统（如已实现 XXX），缺少具体文件、变更和效果，因为没有好/坏示例对比。
  - case 4: 任务完成后没有提哪个节点变了，用户看不到图谱变化，因为协议没有要求报告变更。
  - case 5: task-tree.md 回溯后没有旧 N5，但磁盘仍有 skills/task-tree-grill/SKILL.md 和 skill-routing-log.md 的旧记录；如果模型按记忆认为“已经做过”，就会绕过恢复后的真实任务状态。
- NextIdea: 可以做一个模板复制脚本，把 AGENTS.md + task-tree.md 空模板 + launcher 一键复制到新项目。
