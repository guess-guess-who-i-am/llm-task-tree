# 并行执行与工程入口修复

## 现在怎么用

双击桌面的“打开IDE工程.command”或“打开并行IDE.command”，两者现在都打开真正的源码工程 `/Library/hyf/并行ide/llm-task-tree-macos`。本机地址是 http://127.0.0.1:5518，以启动器输出为准。外层 `/Library/hyf/并行ide/llm-task-tree/open-task-tree.command` 也已指向同一工程，原空模板与旧独立工作区未删除。

在工程树里选中目标节点（例如 N3），编辑它的“下一步思路”，再点“自动并行”。规划按选中节点的 NextIdea 作为目标，而非旧 NextPlan；不选节点时使用当前树的 Next 节点。可以给并行 API 传明确 objective 覆盖该目标。

规划完成后就绪任务自动执行，不需要审批。点并行窗口中的“查看分支树”，可看到本轮独立任务；每个折叠节点有“去到子树”，进入后与普通树一样编辑、使用透镜和单节点直接执行，点“返回主树”回到本轮任务索引。原工程树仍在树选择菜单中，没有替换或复制为另一份权威状态。

每个分支拥有真实 Markdown 子树和完整的任务说明 JSON；整体计划、分支文件及说明均是可进入 Git 的普通项目文件。运行状态和会话索引另存于 `.task-tree-runs`。不会把配置密钥复制进工作区快照。

## 根因：不是单一 API 问题

1. 外层 stub 的 projectRoot 指向外层空模板；工程 stub 又残留 Windows 的 Kit 路径。现修复为实际源码工程及可移植相对 Kit 路径。
2. 桌面旧入口打开 `macos/IDE/workspace`，而不是一直维护的源码树。现默认打开源码工程；旧工作区仍可从它自己的入口打开。
3. `建模世界` 的真实运行记录曾已拆出八个任务，却在 Git `rev-parse` 阶段报“不是 Git 仓库”，零 Worker 启动。并行工作区现在在快照前自动初始化普通目录及尚无 HEAD 的 Git 仓库，只创建空锚点提交，用独立索引快照项目，不动用户暂存区。
4. `execution-tree.json` 只是内部运行图，没有可编辑 Markdown 分支。现在在快照前形成独立的本轮树及每个 Worker 的子树；来源节点和真正执行节点分开，不把所有分支都写到同一个旧节点。
5. 页面未传 treeId、当前子树或选中节点；协调器始终读取 task-tree.md。现在 UI、HTTP、planner、资料上下文和 Worker 按同一来源树取上下文，默认目标使用 NextIdea。
6. MCP 目录发现优先使用继承的 TASK_TREE_PROJECT_ROOT，盖过显式传入的隔离工作目录；有误写原工程的风险。现在显式工作目录优先，每个 Worker 的工具绑定自己的分支树；字段补丁在该分支落盘。共享工具进程按目录和树上下文区分缓存。
7. Worker/冲突处理/协商续接没有检查模型返回的 failed/stopped，就可能继续提交并显示完成。现在失败或停止不会提交或冒充完成，错误及已有隔离结果保留。
8. planner 的独立配置解析漏了全局根 env，导致执行后端能用而 planner 不能用。现在二者共用 DeepSeek 配置解析，不启动 Codex CLI。
9. 工具服务生成的 PID、端口和日志可能混入自动 git add，造成与交付物无关的冲突。现在自动收集不包含这些未跟踪进程文件；任务树与任务元数据的修改仍允许，真实同文件冲突仍走 Git 合并和协调器处理。
10. 桌面符号链接启动时，BASH_SOURCE 指向快捷方式而非源码文件，根目录错算为 `/Users`。最终直接双击测试复现后，两个启动器都改为解析绝对/相对及多层符号链接，链式快捷方式测试通过，真实桌面入口已打开5518。
11. 共用配置解析器原先优先主模型配置，覆盖显式 Planner 配置；全局根 env 存在时，原本本地模拟请求被发到真实上游。两项原有回归先失败，后修复为同一个解析器按调用角色选择覆盖值，没有 Planner 覆盖时仍继承根配置。恢复后两项测试约0.42秒通过；备用地址也按所选配置传递，不混用不同网关的地址。

追加任务先落盘自己的子树与任务说明，再进入正在运行的调度器；不会等先前 Worker 全部结束。依赖任务只在前置结果已合入后启动；不设固定 Worker 数量上限。合并本身串行处理 Git 状态，执行前沿保持并发。

## 测试证据与边界

`server/parallel-pipeline.test.js` 先复现普通目录启动失败、失败误报完成、选树丢失；修复后覆盖真实 Git、显式工具目录隔离、追加任务、运行进程文件排除，以及 NextIdea 优先级。相邻测试覆盖同文件与任务树冲突协商、用户实时修改保留、八/十二/二十个就绪任务并发、续接与共享工具进程。

`scripts/test-parallel-pipeline-ui.mjs` 使用真实 Chromium、HTTP、共享 Worker、任务树 MCP、shell 工具与 Git；只有模型推理使用本机确定性替身。八个独立分支同时请求、一个整合任务在它们全部合入后运行，共十八次实际工具写入；两个模型轮次完成每个分支，自动应用成功，进入/返回子树通过。约 6.46 秒包含浏览器启动、页面加载和切换，不是上游模型速度。函数级计时见 `parallel-pipeline-verification.json`；并发操作耗时的总和不是墙钟耗时。

`scripts/test-parallel-planner-live.mjs` 使用本机实际配置的 DeepSeek 和全局规则/Hook，在隔离树中仅规划。探针约 46.05 秒返回六个独立无依赖任务，覆盖六份指定文件。模型包含说明及 JSON 代码块；测试最初误用整段 JSON.parse，后复用原保存响应通过生产计划解析器，没有重复请求模型。证据见 `parallel-planner-live.json`。

`scripts/test-parallel-workers-live.mjs` 复用上述真实规划响应，避免再次请求 Planner，再让真实 DeepSeek 执行六个独立 Worker。六路确实同时运行，共享同一个常驻工具进程；6/6 成功，六份文档及分支结果全部自动合入，原工程树保持不变，总用时169.704秒。工作区、模型每轮、Hook及工具计时完整保存在 `parallel-workers-live.json`。这次没有模拟 Worker 的推理，也没有让模型修改用户业务树或 IDE 正式源码；六份示例文档用于链路验收，不作为产品说明的正确性证据。

函数级观测：每个 Worker 连接常驻工具服务86–209毫秒；全局 `UserPromptSubmit` Hook 49.181–56.401秒；每 Worker 6–11轮模型请求累计52.012–76.909秒；实际工具及前后Hook总计0.603–0.834秒。模型首轮出现两个连接未成功的尝试，现有重试后第三次200，因此不是全程无网络波动。Git合并7次累计171毫秒、最慢32毫秒，最终应用247毫秒。并发耗时不能直接相加当墙钟时间；提交Hook的内部根因本轮未继续改全局配置，不能把该耗时全部归给 API 或冷启动。

最终 `server/deepseek-run.test.js`、`server/parallel-pipeline.test.js`、`server/planner-global-context.test.js` 合并运行56/56通过；其它未改边界的相邻回归与已有浏览器证据复用。`scripts/test-ide-launchers.mjs` 复现桌面链接失败后，两启动器链式链接均通过。真实Chromium确认5518显示维护中的14节点工程树、ROOT和N3，没有页面错误，截图 `artifacts/ide-project-entry.png`。源码、Kit和插件运行时一致性检查通过。macOS没有PowerShell，树篇幅检查执行其包装脚本实际调用的同一个Node检查器；PowerShell包装入口未做跨平台运行验证。

这些证据不能保证真实业务拆分永远最优、网关永不波动或复杂 Worker 结果永无缺陷。功能链路已经可用，稳定提速与复杂代码产出质量尚不能宣称已验证。现在可以由用户在工程树发起实际改进，并在分支树中查看真实结果。
