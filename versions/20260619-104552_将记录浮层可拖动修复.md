## N1 - 设计 Markdown 节点格式

- Position: 646,892
- Size: 400,720
- Problem: Markdown 需要同时适合人读、模型写、前端解析。
- Approach: 使用固定字段列表，节点标题包含 ID 和标题，边关系放到独立 Edges 区域。
- Input: 节点 ID、标题、位置、问题、思路、输入、输出、指标、批注。
- Output: 一个稳定的 Markdown schema。
- Metrics: 手写不费劲；前端可以解析并保存。
- Notes: 节点不再承担状态和父子关系，关系交给边表达。
- CurrentResult: Markdown schema 继续保留 Input 和 Output 字段作为可解析的数据入口；前端不再把它们直接塞进节点卡片，而是在选中节点左侧显示预览。节点 schema 新增 SelectedSkills 字段，用于保存用户在 skill 推荐面板中选择的能力。
- RootCauseAnalysis: 如果直接从 schema 删除 Input/Output，会破坏历史图和大模型可写格式；真正的问题是主节点视觉负担太重，因此更合适的改法是保留底层字段、改变显示位置。

## N2 - 实现可视化图谱编辑器

- Position: 1275,964
- Size: 670,819
- Problem: 需要一眼看图，并能直接在图上修改节点和关系。
- Approach:
  - 做本地 Web 应用，节点可拖动，连接点可拖线形成边，边可编辑。
  - 图谱编辑会自动保存回 task-tree.md，避免前端状态和 Codex 状态分叉。
  - 单击节点用于选择和拖动，双击节点才进入编辑模式，降低误编辑和难拖动的问题。
  - 前端轮询 task-tree.md，外部修改后会自动刷新图谱。
  - 边标签默认用于拖动摆放，双击边标签才进入编辑模式。
  - 边标签现在是边的控制点，拖动标签会带动边的弯曲中心，标签随边和节点移动。
  - 工具栏提供一键树形排版，将当前图整理为自上而下的标准树结构：根节点在顶部，直接子节点在下一层横向展开。
  - 节点连接点放在节点标题正下方，符合自上而下的树形连接方向。
  - 支持标记当前推进节点和下一步推进节点，并高亮从根节点到目标节点的整条路径。
  - 节点支持 Size 字段和右下角拖拽调整大小；节点内滚轮滚动内容，不再误触发画布缩放。
  - 树形排版按自上而下层级组织，父节点在上，直接子节点在下一层横向展开。
  - 服务端在写入和回退 task-tree.md 前创建版本快照，版本名带“将增加/修改/删除/回退”的原因。
  - 页面右侧增加版本树，显示每个版本的修改原因和时间；点击版本节点会回退，且回退前保留当前版本。
  - 节点主卡片不再显示 Input/Output；单击节点时，在节点左侧弹出同高 I/O 预览框，分别展示输入和输出示例。
  - I/O 预览长内容截取前 400 个字符；如果字段内容是工作区内路径，可以点击通过 /api/file 查看原文件。
  - 为每个项目增加双击入口：打开任务图.cmd 会自动查找或启动本项目服务、分配可用端口，并以应用窗口打开界面。
  - 服务端提供 /api/project，launcher 用它判断某个端口是否属于当前项目，避免多个项目共用固定端口造成混乱。
  - 下一步推进节点的“下一步”输入框下方增加 skill 推荐按钮；点击后根据当前节点和下一步思路检索本地 SKILL.md，在节点右侧显示同高能力面板，可多选并保存到 SelectedSkills。
  - 前端自动保存不再触发版本备份，避免用户在网页里每次输入都生成一个版本；版本备份仍由 Codex 手动改 task-tree.md 或执行回退时创建。
- Input: task-tree.md。
- Output: 浏览器中的任务图谱编辑器。
- Metrics:
  - 能新增节点、拖动节点、连接节点、编辑边、保存 Markdown。
  - 修改节点或边后无需手动点击保存，也能落盘到 task-tree.md。
  - 外部修改 task-tree.md 后，前端能在短时间内同步显示。
  - 边标签能拖动到合适位置，并保存 LabelOffset。
  - 边标签不被节点遮挡；拖动边标签时边也随之变形。
  - 点击树形排版按钮后，节点不重叠，并按从上到下的层级排列。
  - 能一眼看出当前推进路径和下一步候选路径。
  - 能在右侧看到版本原因，点击任一版本可回退，回退不会删除历史版本。
  - 选中节点时能看到左侧 I/O 预览，长文本不撑爆节点，路径可点击打开。
  - 双击项目内的打开任务图.cmd 即可进入对应项目界面，无需记端口或手动 npm start。
- Notes: 第一版先做本地单人使用，不做多人冲突合并。
- CurrentResult: 已形成一个本地任务图编辑器，支持节点、边、超边、自动保存、外部 Markdown 刷新、路径高亮、下一步计划输入、模型维护字段展示、版本快照、点击回退、选中节点时的左侧输入/输出预览、下一步 skill 推荐与多选保存，以及项目级一键入口。现在可双击打开任务图.cmd，它会复用当前项目已运行的服务，或自动找空闲端口启动新服务，并优先用浏览器 app 窗口打开。前端自动保存已改为不创建版本快照，减少版本树噪声。
- RootCauseAnalysis: 之前反复出现“不符合预期”的原因是把问题过早简化为树和表单，没有把用户真正需要的图操作、进度路径、模型维护字段、可视化布局、可回退版本和低摩擦入口当成同一套状态系统设计。入口问题的根因是多个项目同时运行时固定端口会变成人的额外记忆负担，因此入口必须绑定项目目录并自动处理端口。
- CaseStudy:
  - case 1: 最初用左侧目录树和右侧编辑器，用户实际需要的是知识图谱式画布，因此界面抽象错位。
  - case 2: 用 Parent 表达关系，用户实际需要连接点拖线、边可编辑和超边，因此关系模型过窄。
  - case 3: 边标签先被实现成自由便签，用户实际需要边控制点，因此标签和边的语义没有绑定。
  - case 4: 新节点设为下一步后不高亮到根，说明路径搜索不能只按单向边假设，应该按图连通性回溯。
  - case 5: 如果 Codex 直接改 task-tree.md 而没有版本快照，用户只能看到最终状态，看不到为什么改、也不敢回退；因此版本节点必须显示修改原因，并且回退前也要备份当前状态。
  - case 6: 把输入/输出放在主节点中会让节点过高、图谱扫描困难；把它们移到选中节点旁的预览框后，平时看结构，需要时看真实样例。
  - case 7: 用户在图里已经写好了下一步，但还要切回聊天窗口复制，会打断工作流；因此 NextPlan 需要成为可执行入口，而不仅是备注文本。
  - case 8: 从网页直接启动 Codex 涉及权限、工作目录、会话归属和 VS Code 插件历史同步；如果这些边界不透明，用户会更难判断谁在改文件，因此该功能已删除，避免制造新的隐性状态。
  - case 9: 如果每个项目都要求手动 npm start 和记端口，任务图本身又会变成一个需要管理的任务；项目内双击入口把端口选择和复用隐藏起来，更符合“一个项目一个界面”的心智模型。
- NextIdea: 下一步可以把 launcher 做成可复制模板，或者增加“创建桌面快捷方式”的脚本。

## N3 - 让 Codex 同步维护任务图

- Position: 156,954
- Size: 400,720
- Problem: 如果 Codex 完成任务后只在对话里说明，图谱和真实任务进展会再次分叉。
- Approach:
  - 在 AGENTS.md 中加入工作区规则，要求 Codex 推进、完成、拆分或重构任务时同步更新 task-tree.md 的相关节点和边。
  - 每个实质任务开始时先读取 AGENTS.md 和 task-tree.md；如果没有 task-tree.md，就先按 schema 建立任务树。
  - 对宽泛任务先建立或修订整体树，再按 Current/Next/NextPlan 逐节点推进，不一次性执行完整棵树。
  - 当用户请求改变研究方向时，重新判断 Current/Next；必要时新增节点和边，而不是硬塞进旧节点。
  - 开始执行时读取 GraphState.Next/Current 节点的 SelectedSkills；如果有选择，则解析全局 skill 并记录实际使用到 skill-routing-log.md。
  - 当真实输入源或输出物发生变化时，同步更新节点 Input/Output，避免任务图显示旧上下文。
- Input: 当前任务进展、用户反馈、实现变更、task-tree.md 最新内容。
- Output: 与实际工作进度一致的任务图。
- Metrics:
  - Codex 每次完成实质性任务后，task-tree.md 中对应节点或边有最小必要更新。
  - 新任务进入时不会绕过任务树；没有树则建树，有树则先读树。
  - 宽泛任务会先形成可见分解，再逐节点推进。
  - Current、Next、NextPlan 能反映当前研究方向。
- Notes: 规则要求不要使用 active/done/blocked 这类节点状态，而是用节点内容和边关系表达局面。
- CurrentResult: AGENTS.md 已加入任务树入口协议：每个实质任务先读树或建树，宽泛任务先建立整体任务树，再按 Current/Next/NextPlan 逐节点推进；当方向变化时重新定位当前节点。现在还要求读取当前/下一节点的 SelectedSkills，解析可用 skill，实际使用后写入 skill-routing-log.md，并在数据源或产物变化时更新节点 Input/Output。
- RootCauseAnalysis: 仅要求“完成后更新 task-tree.md”还不够，因为模型可能在执行前没有共同任务地图，导致先做后补、节点归属错乱或一次性冲完整棵树。入口协议把“读树/建树/定 Current/Next/逐节点推进”前置，能减少隐性上下文和执行偏航。
- CaseStudy:
  - case 1: 如果用户只说“继续做”，没有先读 GraphState，模型可能沿着旧聊天记忆推进，而不是按当前 NextPlan 推进。
  - case 2: 如果一个新研究方向被硬塞进 N2，前端实现节点会越来越混杂；正确做法是新增节点或切换到 N3。
  - case 3: 如果一开始不建立整体树，模型会边做边改目标，人类看不到哪些节点尚未执行。
- NextIdea: 可以继续把这个协议固化为一份可复用模板，让新项目复制 AGENTS.md、task-tree.md 和 launcher 后即可使用。

## N4 - 分析本地 skill 仓库与自动调用机制

- Position: 2412,668
- Size: 460,720
- Problem: 用户在本项目下放入多个 skill 仓库，需要知道每个 skill 的用途、特点、调用方式，以及如何让大模型自动选择合适 skill。
- Approach: 扫描 CL4R1T4S、gill_with_doc、scientific-agent-skills 中的技能定义与说明，结合 tool/skill routing 相关研究，形成可落地的自动选择机制。
- Input: 全局 skill 根目录（~/.codex/skills、~/.agents/skills、~/.orchestra/skills）、当前节点 SelectedSkills、GraphState.NextPlan、节点 Problem/Approach/Metrics、skill-routing-log.md。
- Output: 中文 skill 推荐面板、SelectedSkills 落盘字段、AGENTS.md 执行协议、skill-routing-log.md 实际使用记录、更新后的节点 Input/Output。
- Metrics: 能列全本地 skill；能说明每类 skill 何时使用；能给出可实现的路由流程、置信度策略和评估办法。
- Notes: 这是一项新的分析任务，和已有任务图工具实现相关但不等同于前端功能开发。
- CurrentResult: 已扫描三个仓库并生成 skill-repos-analysis.md。CL4R1T4S 没有标准 SKILL.md，是提示词/工具档案库；gill_with_doc 有 34 个标准 skill，其中插件主清单暴露 17 个主力工程协作 skill；scientific-agent-skills 有 147 个标准 skill，已在分析文档中完整覆盖。已实现本地 /api/skills/recommend：根据当前节点和下一步思路检索标准 SKILL.md，并在前端右侧能力面板中多选保存到 SelectedSkills。推荐器已改为扫描全局 skill 根目录：~/.codex/skills、~/.agents/skills、~/.orchestra/skills，不再依赖项目下的三个仓库；返回给界面的能力说明已改为中文摘要。已补全调用链条：前端选择后显示已写入任务图，AGENTS.md 要求 Codex 读取 SelectedSkills 并把实际使用写入 skill-routing-log.md。
- RootCauseAnalysis: 不能把“本地有很多 skill”直接等同于“模型会正确自动调用”。根因是 skill 数量大、粒度不一、信任等级不同、触发边界相互重叠；如果把所有 SKILL.md 全塞上下文，会造成 token 浪费和误调用。更稳的方式是先索引 metadata，再按任务图和用户请求召回候选，最后只加载被选中的 skill。之前只扫项目内固定仓库会造成索引不完整，也会让每个项目重复配置 skill；现在改为全局根目录扫描。
- CaseStudy: case 1: CL4R1T4S README 含有要求模型泄露自身指令的攻击性文本，说明参考库不能自动进入执行池。 case 2: gill_with_doc 的 README 明确区分 user-invoked 和 model-invoked skill，说明自动调用应尊重 skill 的调用层级。 case 3: scientific-agent-skills 有 147 个 skill 和大量 references/scripts，说明必须用 progressive disclosure，不能一次性读全。 case 4: 前端自动保存如果每次都触发版本备份，会让版本树被用户输入噪声淹没；备份应该保留给 Codex 修改和显式回退这类关键状态变化。 case 5: 全局目录中诊断能力叫 diagnose 而不是 diagnosing-bugs，说明路由不能只依赖某个仓库的命名。 case 6: 只把 SelectedSkills 写入 Markdown 还不等于“已使用 skill”；必须有 AGENTS 协议和 skill-routing-log.md，把选择、解析、实际使用、结果串起来。
- NextIdea: 可以继续做 skill 启用/隐藏清单，减少推荐噪声；也可以增加一个“复制给 Codex 的下一步执行提示”按钮，把 NextPlan、SelectedSkills 和当前节点摘要组合成短提示。
