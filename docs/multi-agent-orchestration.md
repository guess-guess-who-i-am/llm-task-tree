# 核心主张：多智能体协同编排

> 本文从当前 `task-tree.md` 及其子树出发，说明本项目如何把「多智能体」组织成可编排、可监督、可回退的协同系统。  
> **写法约定**：已落地能力用「现状」标注；尚未完整实现、但与现有图结构/API/协议兼容的能力用「理论可扩展」标注——后者可直接写进叙事，不必假装已经上线。

---

## 0. 一句话

**多智能体协同编排的核心，不是让多个模型同时说话，而是用共享任务图（`task-tree.md`）做权威状态总线，用 GraphState / 执行链 / 子树并行做调度，用节点级多模型与检索工具做分角色执行，用人类在环与版本回退做监督与纠偏。**

聊天是探索；任务图是编排面。

---

## 1. 为什么「编排」比「多模型」更关键

多模型并排回答，只是协同的一种形态。真正决定长程任务成败的是：

| 问题 | 没有编排时 | 有编排时 |
|------|------------|----------|
| 谁现在该做事？ | 靠聊天记忆猜 | `GraphState.Next` + 节点 `NextIdea` |
| 多个 Agent 如何并行？ | 抢同一份上下文 | 折叠 stub + `subtrees/*.md` 分区 |
| 证据从哪来？ | 各说各的 | 知识库 / 联网 / 模型自主 search |
| 分歧如何收束？ | 人肉粘贴 | 节点字段写回 +（理论）裁判融合 |
| 做错了怎么办？ | 对话里改口 | `versions/` 回退 + drift 协议 |

因此本文把「多智能体协同编排」定义为：

```text
编排 = 共享状态 × 调度策略 × 角色分工 × 工具边界 × 人类监督
```

而不是：

```text
编排 ≠ 多窗口同时打开几个 ChatGPT
```

## 2. 与任务图节点的对应关系

下列映射来自当前主树与子树（折叠 stub 见主树，详文见 `subtrees/`）。

| 任务图节点 | 在编排中的角色 | 状态 |
|------------|----------------|------|
| **ROOT** | 总目标：外置大模型隐性上下文，使人类 30 秒内能判断焦点与阻塞 | 进行中 |
| **N1** | 编排语言：Markdown 节点/边 schema，保证人读、模型写、前端解析一致 | 已形成协议 |
| **N2** | 编排界面：可视化图谱；人类指定 Current/Next、编辑边与字段 | 主壳已落地 |
| **N3** | IDE Agent 协同协议：Codex/Cursor 按 AGENTS 读写树，状态与聊天分离 | 子树进行中 |
| **N4** | 能力路由：按节点推荐/选择 Skill，避免全量 skill 塞进上下文 | 分析与机制已有 |
| **N5** | 漂移治理：树回退后磁盘产物不自动等于「已完成」 | 协议已落地 |
| **N6** | **节点内多模型协作**：同子问题上的并行专家角色 | 已落地（并排独立回答） |
| **N7** | **检索层**：本地知识库 + 联网；可注入多模型上下文 | 已落地 |
| **N9** | 编排系统可移植：Kit / 一键更新，多项目复用同一套壳 | 已落地 |
| **N10** | **执行顺序视图**：`scripts/project.json` / `run.json` 与关系图解耦 | 已落地 |
| **ST-P1 / ST-P2** | **子树并行试点**：Coordinator–Worker、冲突面、chain-step 审计 | 试点完成 |

边关系上的编排含义（主树 Edges）：

- `N2 → N6`：界面壳上挂多模型执行面  
- `N2 → N7`：界面壳上挂检索面  
- `N6 ↔ N7`：检索结果可进入多模型上下文；模型也可主动 search  
- `N2 → N10`：关系语义与执行顺序分离，避免「图好看但跑不动」  
- `N3 → N5`：Agent 协同必须带回溯一致性约束

## 3. 编排架构（四层）

```text
┌────────────────────────────────────────────────────────────┐
│ L0  人类监督面                                              │
│     浏览器任务图 · GraphState 焦点 · 版本回退 · 折叠/展开    │
└────────────────────────────┬───────────────────────────────┘
                             │ 权威状态：task-tree.md
┌────────────────────────────▼───────────────────────────────┐
│ L1  调度面（Orchestration）                                  │
│     GraphState.Current/Next · Chain + chain-advance         │
│     执行流程 scripts/* · 子树 Coordinator/Worker            │
└───────────────┬────────────────────────────┬───────────────┘
                │                            │
┌───────────────▼──────────────┐  ┌──────────▼────────────────┐
│ L2a 执行面：IDE Agent         │  │ L2b 执行面：节点多模型      │
│ Codex/Cursor · SelectedSkills│  │ N6 并发 · agent.md 角色     │
│ chain-run / NextIdea         │  │ 临时会话 · 自主 search       │
└───────────────┬──────────────┘  └──────────┬────────────────┘
                │                            │
┌───────────────▼────────────────────────────▼───────────────┐
│ L3  证据与工具面                                             │
│     N7 知识库 embedding · 联网搜索 · Skill 仓库 · 本地命令    │
└────────────────────────────────────────────────────────────┘
```

**关键不变量**：L2 的任何 Agent 都可以提出结论，但**任务是否完成、下一步是谁**，最终以 L0/L1 上的任务图为准，而不是以某次聊天为准。

## 4. 三种已存在的编排模式

### 4.1 焦点编排（单 Agent 串行）

**现状**：人类（或链式 API）指定 `GraphState.Next`；IDE Agent 读树、执行当前节点任务、写回 `CurrentResult` 等字段。

- 协议入口：`AGENTS.md` / `llm-task-tree/AGENTS.task-tree.md`
- 执行依据（链式时）：**Next 节点的 `NextIdea`**，不是 `GraphState.NextPlan`（NextPlan 仅作用户备忘）
- 推进：`POST /api/graph-state/chain-advance`（链式运行时禁止手改 Next）

这是「跟得上模型思路」的最底层编排：每轮只做一个子问题。

### 4.2 节点内多专家编排（N6）

**现状**：同一节点上配置多个 OpenAI-compatible 模型；各自独立 `model-agents/<id>.md`；并发回答；可勾选检索/联网。

设计取舍（来自 N6 子树）：

1. **独立历史**：按 modelId 分开，避免「伪共识」  
2. **临时共享**：页面内可见彼此本轮输出，刷新即清空——防止新隐性记忆污染任务图  
3. **树快照**：运行开始时固定树内容，避免用户边改边跑导致上下文漂移  
4. **自主检索**：模型可输出 search JSON，由服务端执行知识库/联网后再回填（与 N7 耦合）  
5. **密钥边界**：API key 不进 `task-tree.md`

**理论可扩展（N6.NextIdea 已点名）**：增加「融合裁判模型」（judge），把多模型输出归纳为共识 / 分歧 / 盲点 / 推荐写回，再由人类确认后落入 `CurrentResult` / `NextIdea`。  
这不改变编排中枢——裁判仍是任务图上的一个可插拔角色。

### 4.3 子树并行编排（ST-P* / docs/subtree-parallel）

**现状（试点流程）**：

1. 主树折叠大分支为 stub（索引，不存详文）  
2. Worker Agent 各守 `subtrees/<id>-subtree.md`  
3. Coordinator 只读主树 stub、做冲突检查与派活表  
4. 合并回主树：**人类用 UI ⊞ 展开**，避免多 Agent 同时写主树详文  

这是真正的「多智能体系统编排」雏形：

```text
Coordinator ──派活──► Worker-N6 / Worker-N7 / …
       ▲                    │
       └──验收 stub 摘要─────┘
人类 ⊞ 展开 ──► 写回主树权威状态
```

**理论可扩展**：

- 自动 conflict lock（文件级 / 节点级）  
- Worker 完成自动 sync-stub + 通知 Coordinator  
- 与 git worktree 绑定，使代码产物与子树同分区

## 5. 编排对象：角色、状态、工具

### 5.1 角色类型（可组合）

| 角色 | 典型载体 | 职责 |
|------|----------|------|
| 人类监督者 | 任务图 UI | 定焦点、审结果、回退、合并子树 |
| 协调者 | Coordinator prompt /（理论）调度 Agent | 派活、冲突检测、合并冒烟 |
| 执行 Worker | Cursor/Codex + 子树 | 完成一个 NextIdea / 一个子树包 |
| 节点专家 | N6 多模型 | 同题多视角分析、批评、补盲 |
| 检索员 | N7 + 模型 search 工具 | 拉本地/联网证据 |
| 能力顾问 | N4 Skill 推荐 | 缩小可用技能集 |
| 裁判（理论） | Judge 模型 | 融合多专家输出，不直接改图除非人批 |

### 5.2 状态对象（权威 vs 临时）

| 对象 | 权威性 | 说明 |
|------|--------|------|
| `task-tree.md` | **权威任务状态** | 编排中枢 |
| `subtrees/*.md` | 分区权威（未合并前） | 并行包 |
| `versions/` | 历史权威 | 回退依据 |
| `scripts/project.json` + `run.json` | 执行顺序权威 | 与关系图语义分离 |
| `model-agents.json` / 会话轮次 | 配置 / 临时协作 | 不替代任务图 |
| 聊天窗口记忆 | **非权威** | 仅探索 |
| 磁盘代码与索引 | 证据，可能 drift | 以树协议重新验证 |

### 5.3 工具边界

编排的稳定性来自「谁能调什么」：

- IDE Agent：文件系统、终端、按协议写树  
- N6 模型：默认不能随便改树；通过回答影响人类决策，或（理论）经裁判建议写回  
- N7：检索与问答，不决定 GraphState  
- Chain API：只推进焦点，不替用户决定科学结论

## 6. 一次「协同编排」的端到端叙事（可写进介绍）

以下流程混合了现状与理论扩展，适合作为产品/论文叙事主线：

```text
1. 建图
   人类或 task-tree-grill → ROOT + 3–7 子问题节点 + 边依赖

2. 定焦点
   人类点 ◆ Next，或配置 Chain；写下 NextIdea

3. 能力绑定
   N4 推荐 Skill → SelectedSkills；需要文献时打开 N7 库/文件夹范围

4. 并行分解（可选）
   大分支 ⊟ 折叠 → 多 Worker 进子树；Coordinator 盯 stub

5. 节点深思（可选）
   在关键节点开 N6：Main / Critic / Domain Expert 并发
   各模型自主 search；页面内共享临时分歧

6. 收束（理论 + 现状混合）
   Judge 归纳（理论）或人类直接摘录
   写入 CurrentResult / RootCauseAnalysis / NextIdea

7. 推进
   chain-advance 或人类改 Next；执行流程视图对照 scripts 顺序

8. 监督与纠偏
   30 秒看图；不对则 versions 回退；按 N5 规则处理 drift
```

**核心句可反复使用**：  
多智能体不是围绕聊天窗转，而是围绕**可编辑的任务图状态机**转。

## 7. 与常见多智能体框架的差异（叙事对比）

| 常见做法 | 本项目取向 |
|----------|------------|
| LangGraph / 代码状态机为中心 | **Markdown 任务图为中心**，代码是产物 |
| AutoGPT 式自治长循环 | **人类定焦点**；链式每轮只做一个 NextIdea |
| 多 Agent 共享长对话记忆 | **任务图权威 + 临时协作记忆**，防隐性污染 |
| 统一 RAG 广播给所有 Agent | **可广播，也可每模型自主 search**（N6+N7） |
| 只拼装工具调用 | **图结构 + 协议 + 版本 + drift** 一起构成编排 |

## 8. 理论可扩展清单（不必已实现，但与现树兼容）

下列条目均可挂在现有节点上继续演化，不需要推翻中枢：

1. **Judge / Merger 角色（N6）**  
   输入：多模型回答 + 检索片段；输出：结构化共识块，待人类一键写入节点。

2. **角色模板库**  
   `model-agents/` 预置 Planner / Critic / Retriever / Scribe；与 SelectedSkills 交叉绑定。

3. **编排策略配置**  
   节点字段或旁路 JSON：`fan-out`（并行专家） / `pipeline`（检索→写作→核查） / `debate-then-judge`。

4. **子树并行自动化**  
   Coordinator Agent 常驻；文件锁；完成事件；⊞ 前自动 diff 预览。

5. **执行流与多模型打通（N10↔N6）**  
   流程块不仅绑定节点 ID，还可绑定「该步用哪些模型角色」。

6. **知识库按文件夹分库（N7，与近期讨论一致）**  
   编排时指定「本轮 Worker/模型只看哪几个库」——检索隔离本身也是编排的一部分。

7. **跨项目编排**  
   Kit 已解决壳复用；理论上层可做「多项目任务图仪表盘」，仍以每项目 `task-tree.md` 为权威。

## 9. 评价指标（对应 ROOT.Metrics 的编排版）

| 指标 | 含义 |
|------|------|
| 焦点清晰度 | 人类 30 秒内能指出 Current / Next / 阻塞边 |
| 角色可解释性 | 每个输出能追溯到哪个模型/Worker/检索片段 |
| 并行冲突率 | 同文件/同节点被多 Worker 误写的次数 |
| 状态一致性 | 树声称完成 vs 产物存在，漂移是否被显式标记 |
| 收束成本 | 从多专家分歧到可写回 CurrentResult 的人工分钟数 |
| Token 焦点效率 | 执行一轮是否只需 GraphState + Next（及必要局部上下文），而非整段聊天 |

## 10. 结论：什么叫「核心是多智能体协同编排」

对本项目而言，这句话应读成：

1. **中枢是任务图，不是某个模型。**  
2. **编排是调度与边界，不是堆角色。**  
3. **多模型（N6）、检索（N7）、Skill（N4）、链式推进（Chain）、子树并行（ST-P*）都是编排插件。**  
4. **人类始终握有 GraphState 与合并权；Agent 负责执行与提案。**  
5. **未实现的 Judge / 自动 Coordinator / 分库隔离，可以而且应该写进路线图——因为图结构已经为它们留好了挂载点。**

若需要一句话对外：

> 我们做的不是「多个聊天机器人」，而是以共享任务图为总线的多智能体协同编排系统：调度焦点、分区并行、分角色深思、挂接检索与技能，并在人类监督下把结果写回可版本化的外部状态。
