# DeepSeek 工具轮数与上下文交接

本轮保留 DeepSeek 执行后端，不切回 Codex。实现的是本项目的摘要交接，不是调用 Codex 原生压缩接口。官方压缩文档读取返回 HTTP 403，未以未经核实的兼容性假设接入网关。

## 工具执行什么时候结束

`startDeepSeekTurn` 不设工具调用数量或累计任务时限。模型正常结束、用户停止或真实错误才结束执行；API响应头与响应体停滞按单请求监测。普通Stop Hook修复不限次数，详情见 long-task-limits.zh.md。

独立读取的二十路限制是同时执行宽度：超过二十个读取会分批全部处理，不是只执行二十次。写操作之间的顺序约束保留，避免重复写入。

## 长上下文怎么处理

1. 保留两份视图：磁盘和聊天界面的完整文字对话，以及本轮传给模型的工作上下文。整理上下文只改变后者，不删除聊天、不截断导出。
2. 只有压缩阈值以上的上下文、明确交接或网关拒绝容量才整理，不在每次对话或工具返回时例行生成。默认工作窗口为270000 token，超过200000 token 开始压缩；分别由 `MODEL_AGENT_MAIN_CONTEXT_WINDOW` 和 `MODEL_AGENT_MAIN_COMPACTION_THRESHOLD_TOKENS` 配置。扣除4000仅为模型回复预留，不是工具或任务时限。字节数除以2及图片估算都是本地保守估计，不是网关真实容量或官方tokenizer。已成功请求返回非零输入统计后，同模型、同地址、同工具且原输入前缀完整不变时，以真实输入统计为基线，仅对新增内容保守估算，防止反复高估同一批全局规则；该校准不能越过200000压缩阈值。缺失或零统计不覆盖有效基线；前缀编辑、工具变化、模型/地址切换不能复用；真实容量拒绝立即废弃该基线并走原有强制恢复。不可约输入（例如当前用户请求或固定规则本身）不会被删改；若没有可压缩的历史，则保留原文并由网关判断是否接纳。
3. 全局与本轮系统规则、当前用户请求、图片输入、最新调用参数和推理保留原样。普通历史先整理；最新已完成工具结果过大时，原文完整分块交给摘要，只替换模型视图里的工具内容；保持调用ID与回执一一对应，同组原子替换，不插入助手消息打断工具组、不重跑工具。原对象不改，不把工具原文放进持久对话缓存；未完成的工具组不压缩或伪造回执。
4. 摘要复用当前连接与请求恢复，流式调用；更新输入仅为旧记忆加新增资料，不重复发送已覆盖原文。内部摘要/推理不作为聊天回复。普通历史打包、超长单条分片全文处理，尾部不丢。记忆保留目标、更正、约束、精确接口/节点、状态来源、失败及下一动作；最新原话和当前文件高于派生记忆。
5. 摘要、覆盖索引和指纹与完整文字原文原子保存。重启匹配后复用，保留未覆盖原话；编辑旧消息或附件投影不匹配使缓存失效。索引损坏不应用缓存。不长期保存原始工具/推理，但交接记忆可保留带来源的工具报告进展，不能当验证证据。
6. 自动交接与网关拒绝后的强制恢复使用相同的可恢复失败策略：临时连接故障、网关重试耗尽、空摘要和不完整摘要继续重试当前片段；摘要正文超长则继续精炼完整草稿，不设两次尝试的上限。每次请求仍遵守API等待超时，用户取消立即生效；鉴权、永久参数错误和代码异常不伪装为可恢复网络错误。
7. 待整理历史不设总token或分块数量上限，但摘要模型每次请求仍受服务端真实窗口约束。摘要请求被拒超窗时，按Unicode字符边界缩小当前块，成功处理左半后携带其摘要处理右半；后续块复用已获准的较小预算。若旧记忆占用过多，先语义精炼旧记忆再处理增量。所有源片段按顺序完整使用，原文不删除；整次成功才原子替换和持久保存。固定摘要指令加最小片段仍放不下时报告配置边界，而不是无限重发相同载荷。
8. 主执行模型的HTTP容量错误及未开始输出的SSE容量错误仍强制恢复：整理历史或完整已完成工具组后续跑，不重做操作。只剩旧摘要也能再精炼，覆盖索引不变；确实不可缩小的当前规则/请求仍受真实模型窗口限制。永久错误造成的可选整理失败仅暂缓相同压力，任何输入增长可重新整理。指纹阻止无变化请求循环；已开始输出的流从末尾续接，不从头重播。

界面增加“正在整理长上下文，完成后继续执行”。摘要完成、暂缓或失败会解除摘要/重试阶段；只有真正完成任务才显示执行成功。函数级记录包含 `timing.compactions` 的阶段、前后估算量、分片数、耗时，以及 `timing.summaryRequests` 的每地址/模型重试、请求字节、响应头等待、首个内容/推理增量、流读取和总耗时。响应头请求失败也会记入记录；最终错误标注 `context-summary` 阶段，不再把它误当成执行模型故障。估算不等于官方分词器结果。

容量压力记录还包含规则、工具定义、受保护请求、最新工具结果及历史的分项估算；各项独立序列化会有包装开销，不是可直接相加的精确账单。不记录正文或密钥。此次45秒报错机制和回归见 `docs/context-capacity-recovery.zh.md`。

每轮 `timing.rounds[].contextInput` 记录原始粗估、实际用于判断的估算、计数来源和窗口/回复预留。流式响应的累计统计按字段更新，不锁定首个零占位，也不把多帧累计统计相加。计数基线只保留在本轮内存中，不写聊天或磁盘摘要。误摘要的真实网关同题对照与限制见 `docs/context-accounting-stall.zh.md`。

## 中途失败的两条不同链路

已检查的摘要案例中：首轮 GLM 请求约 9.9 秒，写工具约 40 毫秒，之后非流式摘要开始；约两分钟后摘要请求失败，整轮共约 140 秒。修复的是非流式等待、可选摘要失败中断，以及失败计时遗漏，没有延长超时。

另一个现存记录 `314c1e10-e2a3-4045-96af-9245205335b8` 没有摘要事件。第三轮请求 1.45 秒拿到 HTTP 200，随后读取流约 147.6 秒，最终收到 `UND_ERR_SOCKET`。这是传输中断的证据，但仅凭客户端不能区分网关、上游、代理或本机网络；不能宣称已定位唯一责任方。先前工具耗时为 4—448 毫秒，不是这次的主耗时。当前断流恢复保留文字并自动续写，不从头重播工具；连续无数据达到API停滞时限仍结束。完整策略见 execution-recovery-policy.zh.md。

协议依据：Node Web Streams 文档 https://nodejs.org/api/webstreams.html；Stack Overflow 关于 Fetch 取消与超时的讨论 https://stackoverflow.com/questions/71511467/fetch-api-increase-timeout 。本项目分别计量响应头与连续无数据的读取，不把工具/任务总耗时纳入 API 超时。

## 验证与边界

- 原 40 轮行为先复现失败，再验证连续 55 轮工具完成及第 45 轮停止；没有写入重放。
- 长历史提前整理、运行中工具历史整理、摘要停止、网关容量拒绝恢复、最新请求与工具组保留、原文尾部覆盖、修改历史使摘要失效均有针对性测试。
- 本机 HTTP 模型替身 + 真实共享 Worker 完成 50 次工具调用、两阶段上下文整理和真实 Worker 重启；原始对话完整保留，重启续聊复用磁盘摘要，不再次生成。
- 真实已配置网关合成历史只读测试通过：glm-5.3总72.362秒，摘要56.454秒（响应头2.491秒、流53.963秒、首个内容/推理增量2.491秒），执行两轮9.278和6.622秒，工具读取一次小于1毫秒，未重试。摘要约占78%，没有以成功一次宣称上游长期稳定。此实验使用合成历史和固定只读工具，不验证用户业务任务或完整全局Hook效果；详见 summary-recovery-live.json，入口 scripts/test-summary-recovery-live.mjs。
- 摘要是有损语义归纳，不能保证所有旧细节都进入摘要。历史全文仍可回看；不能将流畅摘要当成新证据，也不承诺真实上游稳定或所有任务更快。

测试入口：`server/deepseek-context.test.js`、`server/deepseek-run.test.js`、`server/deepseek-dialogue.test.js`、`server/shared-agent-worker.test.js`。原有停止、编辑重发、全文导出和节点对话回归也保留。
