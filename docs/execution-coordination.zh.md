# 执行协调器：职责、恢复与证据

## 为什么要改

旧系统虽然能拆分和合并，但缺少可追踪的“交付合同”：Worker 说完成，不代表目标文件或指定树节点实际改变。最终检查者只拿到大目标，又要重新猜分工和验收依据。另一个独立问题是摘要精炼反复返回同一超长草稿，模型请求持续发生，任务却不前进。远程医生节点 DOC_S02_CREATE 已实际出现这一状态。

因此增强现有执行协调器，而不是增加一个每一步都要调用模型的主管。正常成功路径不新增模型请求。

## 输入、输出和权限

Planner 接收用户目标、当前树、有效用户历史和分支资料，输出任务分工、目标覆盖关系、共享接口、交付路径/树节点、可观察的验收条件。独立 Planner 和单节点内拆分工具使用同一交付合同定义。写集合是建议，不是写权限限制。

协调器接收这些合同、Worker 事件、真实 Git 工作区和持久检查点，输出执行/恢复/检查状态、交付回执、函数耗时以及最终验收清单。它负责就绪调度、保存成果和定点恢复，不改用户目标、不换模型、不伪造成功，也不能绕过用户停止或最终验收失败。Worker 可以修改实际产物，仍使用全局 Hook 和适用方法。

独立检查 Agent 接收原始目标、共享接口和完整证据清单，在合并候选工作区验证业务效果，可在同一会话修复并复验。最终检查失败就报告失败及根因，不由协调器重新偷偷实现。文件存在和节点变化只是本地交付检查，不代替业务验收。

## 一次任务怎样推进

1. 简单任务直接执行；可分工的任务由现有模型调用提交分工，不再追加主管判断轮。
2. Worker 启动前对明确交付目标保存指纹。普通文件按流式 SHA256；树按指定节点字段比较。多个目标并发读取，绝对项目路径映射到隔离工作区。
3. Worker 完成后检查实际落盘。改错树、只写旁白或只改其他节点，不算交付。已经满足的产物可用 present，需删除的用 delete，不强制无意义改动。
4. 每个分支完成即进入原有整合流水线，不等全部完成才处理 Git。已完成兄弟不会因责任分支重试而重跑。
5. 最终检查者从 .task-tree-runs/coordination-evidence.json 按需读取完整目标、分工、验收条件、接口、文件和节点变更及分支证据；不在 prompt 重复复制全部分支对话。
6. 只有最终检查通过并真正应用后才报告完成。

## 恢复规则

- 缺交付物：保留工作区，将缺失目标交回原责任 Worker。
- 上下文压缩无进展、不可约或明确压缩阶段超时：保存旧对话/答复/失败原因，在同一工作区换新上下文，只继续未完成工作。旧内容完整保存、按需读取，不重新加载整段失败历史。
- Worker 已完成而 Git 临时锁失败：只恢复整合，不再调用 Worker 做一遍。
- 同一个失败签名的自动恢复再失败：终止并给出原因，避免无限空转；用户排障后仍可显式续跑。不是任务时限或工具次数上限。
- 用户停止、权限问题和最终验收失败：不自动恢复。
- 摘要可以多次逐步缩短，但相同超长草稿重复出现会退出；可选压缩失败保留原文，必须压缩才能继续的失败交给协调器处理。

单节点直接执行和多 Worker 都使用相同恢复策略。重启后显式 fresh 续跑仍保留旧线程标识和未完成答复；完成 Worker 的重启恢复仅继续验收。状态文件保留精简恢复记录，不保存原始工具体或内部推理。

## 耗时记录

coordination_delivery_timing 记录 snapshotDeliverables 和 inspectDeliverables 的真实耗时。最终清单有 review.coordination-evidence 计时；原有模型、Hook、Git 命令、工作区函数和最终检查计时继续保留。不能把这些本地机制测试的毫秒耗时当作真实模型整轮延迟。

## 参考和取舍

- Kubernetes controller 使用“目标状态—观察状态—调和”的事件驱动模式：https://kubernetes.io/docs/concepts/architecture/controller/
- Temporal 区分可重试失败和非重试失败：https://docs.temporal.io/encyclopedia/retry-policies
- Stack Overflow 关于 Worker 退出后的长任务恢复：https://stackoverflow.com/questions/13307067/restarting-long-tasks-in-a-group-after-a-worker-died 。整组重跑会重复成功分支，不适用于本 IDE；这里保留各分支工作区并定点恢复。

## 验证与部署边界

已通过本地 224 项定向回归，包含真实 Git 隔离/合并、HTTP 模拟模型的 Hook/skills/工具/独立检查、100 个就绪 Worker 调度、摘要无进展与定点恢复。另补充了显式停止后 fresh 续跑的真实 HTTP 路由回归。模拟模型不能证明真实模型质量或网关稳定；远程实际续跑需独立记录结果。

发布使用独立内容哈希 runtime，保留旧 runtime 和停止时的状态备份；只重启当前项目服务，不影响其他服务。恢复使用原 runId 和原工作区，不重新创建任务。模型维持 gpt-6.1-sol，预期窗口 270K、压缩阈值 200K，仍须核验实际配置。

## 2026-10-22：真实恢复暴露的检查模式不一致

高级设置节点的真实失败并非 API 超时：Worker 已产出说明片段，最终检查需要把说明写回指定节点，但检查者没有继承普通执行者的 TASK_TREE_QUALITY_MODE=advisory。共享 Worker 因质量模式不同创建严格 MCP，检查整个已存在的 24,258 字节子树，并以 12,288 字节上限拒绝定点修改。进程常驻和并行调度都无法修复这一配置边界错误。

修复在调用方统一 IDE 角色配置：独立 Planner、并行 Worker、单节点及并行最终检查者、合并处理者均使用已有 advisory 模式。严格 CLI/MCP 仍保留严格行为，结构、GraphState 和授权检查不变；不是全局取消门禁，也不要求 Worker 整理未分配的兄弟节点。Node 官方 child_process 文档说明子进程环境来自调用方 env，未传的会继承默认 process.env，不会自动继承另一个任务的配置：https://nodejs.org/api/child_process.html 。本次访问相关 Stack Overflow 页面被 403 拒绝，不把未读页面作为证据。

第二个问题是验收目标漂移：用户要求解释节点概念，旧检查提示却只描述“检查功能、运行流程”，检查者把未运行的医疗业务服务也视为失败依据。现在明确以原用户目标及交付合同验收：解释任务核对事实、可理解性和实际节点回写；确有软件行为改动仍须验证，不能把文档测试冒充业务实测。
